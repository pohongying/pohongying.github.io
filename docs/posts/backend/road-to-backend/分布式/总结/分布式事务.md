# 分布式事务

# 分布式事务解决方案：
简化解析 在分布式系统中，需保证“多个操作要么全成、要么全败”，以下按强一致性、最终一致性两类，简化解析各方案的核心逻辑与优劣势。

## 一、强一致性方案 
1. 两阶段提交（2PC）

 分为准备、提交两阶段：协调者先询问所有参与节点是否准备就绪，全部就绪则下达提交指令，否则下达取消指令；优点是逻辑简单、能保障强一致，适合传统数据库场景；缺点是参与节点需等待协调者指令，易阻塞、效率低，且协调者故障会导致事务僵死，提交阶段还可能因网络问题出现数据不一致。

2. 三阶段提交（3PC） 在2PC基础上增加询问阶段，先确认节点能力、再预提交锁定资源、最后正式提交，且支持超时自主决策；优点是减少资源锁定时间、降低阻塞，协调者故障后容错性提升，不一致风险降低；缺点是交互步骤增加，系统复杂度和沟通成本上升，协调者仍为关键节点，极端情况仍有不一致可能。

## 二、最终一致性方案 
1. 补偿事务（TCC)： 拆分为Try（检查预留资源）、Confirm（确认执行）、Cancel（回滚释放资源）三阶段；优点是灵活适配不同业务，无阻塞、效率高，支持跨服务场景；缺点是需为每个业务定制三阶段逻辑，开发成本高，且Confirm/Cancel需保证幂等性，实现难度大。 

2. 可靠消息最终一致性方案： 依赖消息队列，发起方执行本地事务后发送消息，接收方消费消息并执行事务，失败则重试；优点是服务间解耦、效率高，适合非实时强一致需求；缺点是依赖消息队列可靠性，消息丢失或重复会引发问题，消息状态管理和幂等处理复杂。 

3. Saga模式： 将复杂事务拆分为多个本地短事务，正向按序执行，失败则反向按序补偿；优点是适配长流程、多步骤业务，灵活性高；缺点是补偿前会存在临时数据不一致，每个短事务及补偿逻辑需精心设计，维护成本高，且缺乏事务隔离性。 

 4. 最大努力通知型： 发起方完成本地事务后，向接收方发送通知，失败则按策略重试，重试上限后停止；优点是实现简单、对现有系统入侵小，不阻塞主业务；缺点是无法保证接收方一定执行成功，重试策略难平衡效率与资源，异常时需人工介入。 

 5. 本地消息表： 发起方执行本地事务时，在数据库消息表记录待通知信息，通过定时任务推送消息，接收方执行后反馈，发起方标记消息完成；优点是基于传统数据库，实现可靠、简单；缺点是消息表与业务表共用数据库，高并发下易成瓶颈，业务与通知逻辑耦合，不利于维护。
