# AQS

## AQS是什么？一个万能的“排队叫号系统”

AQS中的CLH队列，本质上是一个用于管理等待线程的、无锁化的双向链表。当一个线程尝试获取锁失败时，它会将自己包装成一个节点，并通过一个乐观的自旋循环，**使用CAS（比较并交换）原子操作来尝试将自己设置为新的队尾**。这个CAS操作是关键，它能保证在任何时刻，只有一个线程能成功地“抢”到队尾的位置并入队；其他同时竞争的线程会因比较失败而自动重试，直到成功为止。整个入队过程完全不需要传统的锁来保护队列本身，从而极大地降低了线程排队时的系统开销和冲突，实现了高效的并发线程管理。

想象一下，AQS就是一个设计精良的**银行排队叫号系统**。

这个系统有两个核心部件：

1. **一个柜台叫号器（**`**state**`**变量）**：这个叫号器是一个整数。比如，它的数字是`0`时，表示“柜台空闲，可办理业务”；是`1`时，表示“柜台正忙”。
2. **一个等候区（CLH等待队列）**：这是一个非常守秩序的双向队伍，所有没能抢到号的线程，都会在这里排队等待。

AQS的目标就是管理好这个`state`和这个等待队列，让多线程访问共享资源时井井有条。像我们熟悉的`ReentrantLock`、`Semaphore`等，其实都是基于这个“排队叫号系统”定制的。

***

## 核心流程：抢号、排队、叫号

一个线程（比如“线程张三”）想要执行一段加锁代码，它的流程是这样的：

1. **尝试抢号 (tryAcquire)**：张三上来先看一下叫号器`state`是不是`0`。如果是，说明柜台空闲，他运气好，直接用**CAS**（Compare-And-Swap，一种“比较并替换”的原子操作，确保同一瞬间只有一个人能成功）把`state`从`0`改成`1`。然后他就占有了锁，开始办理业务（执行同步代码）。
2. **抢号失败，进入等候区排队 (addWaiter)**：如果张三发现`state`是`1`，或者他尝试用CAS修改`state`时失败了（说明别的线程捷足先登了），他就抢号失败。这时，他会：
   * 把自己包装成一个“排队小纸条”（`Node`对象）。
   * 走到等候区的队尾，把自己这个“小纸条”挂在队伍最后面。
   * 然后就拿出手机开始刷，进入**休眠状态**（`LockSupport.park()`），不再浪费CPU时间。
3. **办理完业务，释放并叫下一个号 (release)**：当占有锁的线程（比如“线程李四”）办完业务后，他会：
   * 把叫号器`state`从`1`改回`0`。
   * 看一眼等候区有没有人在排队。
   * 如果有人，就**叫醒排在最前面的那个人**（`LockSupport.unpark()`），让他去尝试抢号。
