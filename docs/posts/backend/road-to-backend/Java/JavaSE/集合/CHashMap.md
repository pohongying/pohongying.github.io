# CHashMap

### 核心要点概括

`ConcurrentHashMap` 在 JDK 1.8+ 的高性能和高并发性主要依赖于四大基石：

1. **极细的锁粒度**：放弃了 `Segment` 分段锁，改为对每个哈希桶的**头节点**进行加锁，极大减少了锁竞争。
2. **CAS 无锁操作**：在关键路径（如插入首个节点、更新状态）上使用 CAS（Compare-And-Swap）操作，实现了高效的无锁并发。
3. **协作式扩容机制**：扩容时，所有执行写操作的线程都会**共同参与**数据迁移，而不是阻塞等待，将扩容的性能影响降到最低。
4. `volatile`\*\* 保证可见性\*\*：核心数据（如 `table` 数组、节点指针）使用 `volatile` 修饰，确保了读操作在无锁的情况下也能安全地获取最新数据。

***

### 1. 锁的粒度：从“分段”到“分桶”

锁的粒度，指的是加锁对象的大小。粒度越小，意味着锁的范围越小，不同线程之间发生冲突的可能性就越低，并发能力就越强。

* **JDK 1.7 (分段锁 - 中等粒度)**
  * **原理**：`ConcurrentHashMap` 内部有一个 `Segment` 数组，每个 `Segment` 是一个独立的小哈希表，并持有一把 `ReentrantLock` 锁。
  * **加锁方式**：当一个线程需要修改数据时，它会先定位到 key 所在的 `Segment`，然后\*\*锁住整个 \*\*`Segment`。
  * **效果**：只要多个线程操作的 key 不在同一个 `Segment` 中，它们就可以并行执行。并发度理论上等于 `Segment` 的数量（默认为 16）。
* **JDK 1.8+ (桶锁 - 极细粒度)**
  * **原理**：取消了 `Segment` 结构，整个 Map 只有一个 `table` 数组。
  * **加锁方式**：当一个线程需要修改一个**非空**的哈希桶时，它只会用 `synchronized` **锁定该桶的第一个节点**。
  * **效果**：只有当多个线程**精确地操作同一个哈希桶**时，才会发生锁竞争。相比于锁定整个段，这种锁的粒度要细得多，因此并发性能得到了巨大的提升。

### 2. 为什么锁的粒度变了？(从 1.7 到 1.8 的演进动机)

这种演进主要是为了解决 JDK 1.7 分段锁设计的固有瓶颈，并更好地利用现代多核 CPU 的性能。

1. **解决分段锁的“伪共享”问题**：在 1.7 中，多个 key 即使不同，只要它们的哈希值最终定位到同一个 `Segment`，就会竞争同一把锁，导致性能下降。这种“段内竞争”在高并发下是明显的瓶颈。1.8 的桶锁则基本消除了这个问题，除非 key 的哈希值完全一样（即哈希冲突）。
2. **降低内存开销**：每个 `Segment` 都是一个功能完备的哈希表，有自己的数组和锁对象，这带来了较大的内存开销。1.8 的结构更加扁平化和紧凑，内存利用率更高。
3. **利用 JVM 对 **`synchronized`** 的优化**：随着 Java 版本的迭代，JVM 对 `synchronized` 关键字进行了大量优化，包括锁膨胀（偏向锁 -> 轻量级锁 -> 重量级锁）。在绝大多数情况下（无竞争或低竞争），`synchronized` 的性能已经与 `ReentrantLock` 相差无几，甚至更好。1.8 的设计正好利用了这一点：锁的粒度极细，意味着锁竞争的概率很低，`synchronized` 可以保持在轻量级锁状态，开销极小。

### 3. 扩容原理概括

`ConcurrentHashMap` 的扩容机制是其“并发”特性的完美体现，核心思想是\*\*“协作”**而非**“阻塞”\*\*。

* **触发**：当 Map 的元素数量达到阈值时，第一个执行 `put` 操作的线程会触发扩容。
* **协作**：该线程会开始数据迁移，创建一个两倍于旧容量的新 `table`。在此期间，如果其他线程也尝试 `put` 数据，它们**不会被阻塞**，而是会**检测到正在扩容的状态，并自动加入到数据迁移的任务中**。每个线程会分担一部分桶的迁移工作。
* **迁移中的读写**：
  * 迁移过程是从后往前逐个桶进行的。
  * 当一个桶的数据被完全迁移后，会在旧 `table` 的该位置放一个特殊的\*\*`ForwardingNode`\*\*（转发节点）。
  * 如果此时有 `get` 或 `put` 请求访问到这个 `ForwardingNode`，它会被告知数据已经迁移，并被\*\*自动重定向到新的 \*\*`table` 去执行操作。
  * 这保证了在整个漫长的扩容过程中，Map 始终对外可用，读写操作不会中断。

### 4. CAS (Compare-And-Swap) 的相关操作

CAS 是一种无锁原子操作，是实现高性能并发数据结构的基础。它的逻辑是：“我认为内存地址 V 的值应该是 A，如果是，那么就把它更新为 B，否则什么都不做并告诉我失败了”。

在 `ConcurrentHashMap` 中，CAS 被用在最关键、最频繁的操作路径上，以避免加锁带来的性能开销。

1. **插入桶的第一个节点**：当一个 `put` 操作发现目标桶是空的时候，它不会加锁，而是直接使用 **CAS** 尝试将新节点设置为该桶的第一个节点。这是最高频的场景之一，通过无锁化，极大地提升了 `put` 操作的平均性能。
2. **更新和协调状态 (**`sizeCtl`**)**：`sizeCtl` 这个核心变量的所有状态变更（如初始化、标记扩容状态、更新扩容线程数）都是通过 CAS 完成的。这保证了在没有全局锁的情况下，整个 Map 的状态可以被安全、原子地修改和协调。
3. **更新元素数量 (**`size`**)**：`size` 的增减也是通过 CAS 操作 `baseCount` 和 `CounterCell[]` 数组来完成的。在高并发下，线程会将计数压力分散到不同的 `CounterCell` 中，避免了所有线程竞争同一个计数器，从而提高了计数的并发能力。

### 一、是什么？ (What is ConcurrentHashMap?)

`ConcurrentHashMap` 是一个**支持高并发更新和查询**的线程安全的哈希表。它在保证线程安全的同时，提供了远超 `Hashtable` 和 `Collections.synchronizedMap` 的性能。它的设计在 JDK 1.7 和 JDK 1.8+ 中有重大的演进，我们主要以后者为核心进行分析，因为它更加先进和常用。

#### 1. 基本成员变量 (JDK 1.8+)

* `transient volatile Node<K,V>[] table;`
  * **哈希表数组**：存储桶（bucket）的数组，与 `HashMap` 类似。使用 `volatile` 修饰，保证其在多线程之间的**可见性**。当一个线程修改了 `table` 的引用（例如初始化或扩容后），其他线程能立刻看到这个变化。
* `private transient volatile Node<K,V>[] nextTable;`
  * **扩容时使用的新数组**：当进行扩容时，这个数组用于临时存放迁移的数据。同样使用 `volatile` 修饰。
* `private volatile int sizeCtl;`
  * **核心控制变量**：这是一个多功能变量，它的值决定了 `ConcurrentHashMap` 的状态：
    * **负数**：表示哈希表正在进行**初始化**或**扩容**。
      * `-1`：表示正在初始化。
      * `-(1 + n)`：`n` 表示正在参与扩容的线程数。
    * **0**：默认值，表示哈希表尚未初始化，将在首次插入时使用默认容量进行初始化。
    * **正数**：表示下一次触发扩容的**阈值**（即 `capacity * loadFactor`）。
* `private static final sun.misc.Unsafe U;`
* `private static final long SIZECTL;`
* `private static final long ABASE;`
  * **Unsafe & CAS**：`ConcurrentHashMap` 底层广泛使用了 `sun.misc.Unsafe` 类提供的 **CAS (Compare-And-Swap)** 操作。这是一种**乐观锁**技术，允许在不加锁的情况下尝试进行原子更新，是其高性能的关键之一。

#### 2. 核心思想演进

* **JDK 1.7 - 分段锁 (Lock Striping)**
  * `ConcurrentHashMap` 内部由一个 `Segment` 数组构成。每个 `Segment` 本身就像一个小型的 `Hashtable`，它继承了 `ReentrantLock`。
  * 当对数据进行操作时，不是锁定整个 Map，而是根据 key 的哈希值定位到对应的 `Segment` 并\*\*只锁定那一个 \*\*`Segment`。
  * 这使得多个线程只要操作的不是同一个 `Segment`，就可以完全并发执行。其并发度理论上就是 `Segment` 的数量（默认为 16）。
* **JDK 1.8+ - CAS + **`synchronized`** (锁粒度更细)**
  * \*\*摒弃了 \*\*`Segment`，整体结构更像 `HashMap`（数组 + 链表/红黑树）。
  * 锁定的粒度被大大减小，不再是锁定一个段，而是**只锁定每个桶的头节点**。
  * 写操作时，如果桶是空的，则使用 **CAS** 尝试原子性地插入头节点。
  * 如果桶不为空，则使用 `synchronized` 关键字**锁定该桶的头节点**，然后再进行后续的插入或更新操作。
  * 这种设计使得只要线程操作的不是**同一个桶**，就可以完全并发。其并发度远高于 JDK 1.7。

### 二、为什么？ (How does it work?)

#### 1. `put(K key, V value)` 原理 (JDK 1.8+)

`put` 操作是 `ConcurrentHashMap` 设计精髓的最佳体现，它在无锁（CAS）和加锁（`synchronized`）之间做了精妙的切换。

1. **初始化检查**：
   * 检查 `table` 是否为 `null`。如果是，则调用 `initTable()` 方法进行初始化。初始化过程是线程安全的，通过 \*\*CAS 操作 \*\*`sizeCtl` 来保证只有一个线程能成功进行初始化。
2. **定位桶**：
   * 计算 key 的哈希值，并通过 `(n - 1) & hash` 定位到 `table` 数组中的桶索引。
3. **处理桶内插入**：
   * **Case 1: 桶为空 (无锁)**
     * 如果定位到的桶是空的 (`table[i] == null`)，则使用 **CAS** (`casTabAt`) 操作尝试将新节点直接设置为该桶的头节点。
     * 如果 CAS 成功，说明没有竞争，操作完成。
     * 如果 CAS 失败，说明在同一时刻有另一个线程抢先一步占据了这个桶，此时会进入下一轮循环，重新处理（此时桶已不为空）。
   * **Case 2: 桶不为空 (加锁)**
     * 如果定位到的桶已经有节点存在，则进入加锁逻辑。
     * 使用 `synchronized (f)`，其中 `f` 是该桶的**头节点**。通过锁定头节点，可以保证同一时间只有一个线程能修改这一个桶内的数据结构，而其他线程操作其他桶时则完全不受影响。
     * 在 `synchronized` 代码块内部，遍历链表或红黑树：
       * 如果找到 key 相同的节点，则更新其 value 值。
       * 如果未找到，则将新节点追加到链表末尾。
       * 在追加后，检查链表长度是否达到阈值（默认为 8），如果达到则将链表转换为**红黑树**，以优化后续查询性能。
   * **Case 3: 正在扩容**
     * 如果在 `put` 过程中发现桶的头节点是 `ForwardingNode`，说明 `table` 正在扩容。当前线程会**加入并帮助进行扩容**（调用 `helpTransfer` 方法），而不是等待或阻塞。这种**协作式扩容**极大地提高了并发扩容的效率。
4. **更新 size 并检查扩容**：
   * 插入成功后，调用 `addCount()` 方法原子性地更新 Map 的 `size`。
   * `addCount()` 内部会检查当前 `size` 是否超过了扩容阈值 (`sizeCtl`)，如果超过，则会触发**扩容**流程。

#### 2. `get(K key)` 原理

`get` 操作的设计目标是**全程无锁**，这也是它查询性能极高的原因。

1. **定位桶**：计算哈希值，找到对应的桶。
2. **遍历查找**：
   * 由于 `table` 数组和 `Node` 节点的 `next` 指针都是用 `volatile` 修饰的，这保证了读线程总能看到最新的数据结构。
   * 直接遍历桶内的链表或红黑树，比较 key 是否相等，找到则返回 value。
   * 整个过程**不涉及任何加锁**，因此多个读线程之间可以完全并发执行，且不会被写线程阻塞（除了在极端的树化或扩容迁移的瞬间）。

#### 3. 扩容 (Resizing) 原理

扩容是 `ConcurrentHashMap` 中最复杂但又最巧妙的设计。

1. **触发**：
   * 当 `addCount()` 方法发现 `size` 超过阈值时，会由第一个线程发起扩容。
   * 该线程会创建一个容量为原来两倍的 `nextTable`，并使用 CAS 更新 `sizeCtl` 为一个负数，标志着扩容正式开始。
2. **协作迁移 (**`transfer`**)**：
   * **任务划分**：系统会将旧 `table` 的所有桶划分成多个任务（strides）。
   * **多线程协作**：发起扩容的线程和后续在 `put` 时发现正在扩容的线程，都会根据 `sizeCtl` 的状态来领取任务，并行地进行数据迁移。一个线程负责迁移一部分桶。
   * **迁移过程**：
     * 线程在迁移一个桶之前，会先 `synchronized` 锁定该桶的头节点，防止其他线程修改。
     * 遍历桶内的所有节点，重新计算每个节点在新表 `nextTable` 中的位置。由于容量是2倍，一个旧桶的节点只可能分布到新表的两个位置：`i` 或 `i + oldCapacity`。
     * 将节点迁移到 `nextTable` 相应的位置。
     * 当一个桶的所有节点都迁移完毕后，会在旧 `table` 的该桶位置上放置一个特殊的 `ForwardingNode`。
3. **完成**：
   * 当所有桶都迁移完成，最后由一个线程将 `table` 的引用指向 `nextTable`，并更新 `sizeCtl` 为新表的扩容阈值。
   * 在扩容期间，`get` 操作如果遇到 `ForwardingNode`，会自动**转发**到 `nextTable` 去查找，保证了扩容期间读操作的连续性。

### 总结

| 操作 | JDK 1.7 实现原理 | JDK 1.8+ 实现原理 | 优点 |
| :--- | :--- | :--- | :--- |
| `put` | **分段锁 (Segment Lock)**：对 key 所在的 `Segment` 加 `ReentrantLock` 锁。 | \*\*CAS + \*\*`synchronized`：对桶的头节点加 `synchronized` 锁，或在桶为空时使用 CAS。 | **锁粒度极细**，并发性能极高。 |
| `get` | **全程无锁**：`Segment` 内的 `volatile` 保证可见性。 | **全程无锁**：`volatile` 保证可见性，性能极佳。 | **读操作无阻塞**，速度快。 |
| `size` | 累加所有 `Segment` 的 `count`。在并发高时可能不准确，需要加锁多次计算。 | 使用 `baseCount` 和 `CounterCell[]` 维护。通过 CAS 更新，在低竞争时性能好，高竞争时分散压力到 `CounterCell`。 | **size 计算更高效准确**。 |
| **扩容** | 对单个 `Segment` 内部进行扩容，不影响其他 `Segment`。 | **协作式扩容**：所有写线程共同参与数据迁移，速度快。 | **扩容期间服务不中断**，吞吐量更高。 |
